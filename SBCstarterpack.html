COMPUTE BOARD SETUP GUIDE

WGtech AI Starter Kit
Metis Compute Board

Start the Voyager SDK container on the board, restore Docker Compose and MediaMTX, then launch the Starter Kit dashboard. Every command is explained: what it does and why you need it. Follow the sections in order.

What you will do
  • Prepare the Ubuntu PC to talk to the board over USB
  • Start the Voyager SDK container and confirm the AIPU opens
  • Install Compose and MediaMTX, then launch the kit
⏱ Estimated Time
  • Active setup time: 30–60 minutes
  • Total time (including downloads & the first model compile): 2–4+ hours

Before you begin. Follow the sections in order. Step 2 points you to Axelera's official flashing documentation, and the rest assumes a correctly flashed Compose Board with Ethernet internet.

§ 01Hardware Requirements

The Metis Compute Board is a complete unit: the AIPU is on the board, so there is no card to seat and no PCIe HAT to stack. You will need the following around it:

COMPONENT NOTES
Metis Compute Board RK3588 SBC with integrated Metis AIPU, supplied as one unit
Power supply 12V, 7A DC adapter with a 5.5 mm (outer) x 2.5 mm (inner) barrel connector. An underpowered supply causes random crashes and AIPU instability
Storage SD card or eMMC/NVMe as specified for your board. Class 10 / A2 or faster shortens boot and install times
HDMI display + cable Check the board's connector type before buying a cable
USB keyboard + mouse For initial setup
Ethernet (preferred) or Wi-Fi Ethernet is strongly preferred for reliability during large downloads
USB-C data cable + Ubuntu PC Used for adb and for copying files to the board. Charge-only cables will not work
One or more RTSP IP cameras On the same subnet as the board. H.264 or H.265 supported. A USB webcam works too
Integrated AIPU The Metis Compute Board has the AIPU built in. There is no physical accelerator installation: no card, no M.2 slot, no PCIe HAT to worry about.

1.1Where each command runs

Every step is tagged with where to run it. Check your prompt first:

Prompt Where you are What runs there
wg-tech@...-Notebook-PC PC adb, downloads, adb push
root@antelao-3588 Board host docker, docker compose, kit scripts
ubuntu@antelao-3588:~/voyager-sdk Container axdevice, make (no docker here)
Tip: "command not found" almost always means the wrong shell. Back up /home/antelao/shared before changing anything, because it is the only folder that survives container restarts.

§ 02Flash the Operating System

Flash the board's OS image following Axelera's official documentation for your board revision. Axelera's guide is authoritative: the image, tool and procedure vary by board, so follow theirs rather than a generic one.

Start at docs.axelera.ai and the Voyager SDK repository. Use the image and flashing tool they specify for the Compose Board.

Once flashed, boot the board and confirm you are on the right platform:

BASH
uname -m
cat /proc/device-tree/model
aarch64
...RK3588...
  • uname -m prints the CPU architecture. aarch64 means ARM 64-bit, which is what this board needs
  • cat /proc/device-tree/model prints the board model name the system reports, which should mention RK3588
If uname -m does not report aarch64, or the model does not mention RK3588, stop and recheck the image. The rest of this guide assumes a correctly flashed Compose Board.

§ 03First boot & Voyager SDK container Board host

Open a terminal on the board, check it is online, then start the Voyager SDK container.

You are root on the board. The prompt looks like root@antelao-3588:~# (note the # and root@). Because you are already root, board commands in this guide are shown without sudo. Run them exactly as written. Commands tagged PC run on your Ubuntu PC and may use sudo.

3.1Install and start adb

BASH
sudo apt update
sudo apt install adb
adb kill-server
adb start-server
* daemon not running; starting now at tcp:5037
* daemon started successfully
  • apt update refreshes the package list. On a fresh install, skipping it makes adb "not found"
  • apt install adb installs the Android Debug Bridge, the tool that opens a shell on the board over USB and copies files
  • adb kill-server stops any stuck adb background process
  • adb start-server starts a clean one on port 5037
Tip: Empty list? Use a data-capable cable, replug it, and repeat adb kill-server and adb start-server.

3.1 aCheck the board is detected

BASH
adb devices -l
List of devices attached
0123456789ABCDEF       device usb:2-5 transport_id:4

Why: Lists connected devices (-l adds details). Note your usb:X-Y value, which identifies the board when you have several devices.

3.1 bOpen a terminal on the board

Use any one of these. The on-screen terminal needs the HDMI display and keyboard from section 1: after boot, click the shell icon in the top-left corner. Over USB-C use adb (it must be installed on your PC):

BASH
adb -s usb:2-5 shell

If adb is not installed on your PC yet, set it up first (run these on your PC, not the board):

3.2Connect to the network and check the internet

Ethernet is plug-and-play. Confirm you are online and note the board's IP, which you will use to reach the dashboard from your laptop later:

BASH
ping -c 3 8.8.8.8
hostname -I
3 packets transmitted, 3 received, 0% packet loss
192.168.1.50      (your IP will differ)
  • ping -c 3 8.8.8.8 sends 3 test messages (-c 3) to 8.8.8.8, a public Google server. Replies mean the board has internet
  • hostname -I prints the board's IP address

"Network is unreachable" or 100% packet loss means check the Ethernet cable and router.

Tip: Write down the IP from hostname -I (the first address). You will open http://<that-ip> from another machine on the same network once the dashboard is running.
Now switch to the board. Connect the Rockchip board to a monitor with the HDMI cable, open the terminal on the board (click the shell icon in the top-left corner), and continue the process from here in the Rockchip terminal. Its prompt should look like root@antelao-3588:~#.

3.3Check versions and Docker

BASH
cat /etc/os-release
cat /sys/class/metis/version
docker --version
docker ps -a
docker images
  • cat prints a file. The first shows the OS (BSP) version, the second the Metis driver version, which must match your SDK (this setup used driver 1.4.16 with SDK 1.6.0)
  • docker --version confirms Docker is installed
  • docker ps -a lists all containers, including stopped ones. Exited is normal
  • docker images lists downloaded images

You want one Voyager container and one image.

3.4Download the SDK image (about 6 GB)

BASH
cd /home/antelao
./setup_axelera_environment.sh 1.6.0

cd moves into the folder holding the scripts. The script downloads the SDK Docker image for version 1.6.0. Skip it if docker images already lists axelera-sdk-ubuntu-2204-arm64:1.6.0.

This can take a while on first run depending on how old the image is. Use Ethernet if you can.

3.5Start the container

BASH
python3 start_axelera.py start --container-name "Voyager-SDK" --version "1.6.0"
[INFO] Initializing Voyager SDK container 'Voyager-SDK' (Version 1.6.0)
[INFO] Existing container 'Voyager-SDK' detected.
ubuntu@antelao-3588:~/voyager-sdk$

The helper script creates the container, or restarts it if it exists, and opens a shell inside it. --container-name names it and --version picks the SDK image. A prompt starting with ubuntu@ means you are now inside.

3.6First-time build (inside the container)

BASH
make clobber-libs && make operators

make clobber-libs clears old libraries and make operators builds the AI operators. && runs the second only if the first succeeds. It needs internet, takes several minutes and must not be interrupted. Skip it if axdevice already works.

3.7Test that the AIPU opens (inside the container)

BASH
cd ~/voyager-sdk
source venv/bin/activate
axdevice
Device 0: metis-0:1:0 4GiB metis-compute-board flver=1.5.0 bcver=7.1 clock=800MHz(0-3:800MHz) mvm=0-3:100%
  • source venv/bin/activate turns on the SDK's Python environment. The prompt gains (venv)
  • axdevice lists Metis accelerators. Seeing Device 0 proves the driver and SDK work together
"Failed to open device"? The driver and SDK versions likely differ. Compare the host's cat /sys/class/metis/version with the SDK version.
Tip: exit leaves the container and stops it. Restart it later with docker start Voyager-SDK from the host.

§ 04Docker Compose Board host

The kit launches several services together with Compose, and it is not on the board by default.

BASH
mkdir -p ~/.docker/cli-plugins
curl -SL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-aarch64 -o ~/.docker/cli-plugins/docker-compose
chmod +x ~/.docker/cli-plugins/docker-compose
docker compose version
Docker Compose version v5.5.1
  • mkdir -p creates the plugin folder (-p means no error if it exists and creates parents)
  • curl -SL ... -o file downloads: -S shows errors, -L follows redirects, -o sets the output file. The aarch64 file is the ARM 64-bit build the board needs
  • chmod +x marks it executable
  • docker compose version proves Docker finds the plugin
Tip: ~ is /root for root, so run the kit as the same user. Any version number is fine if one prints.

§ 05MediaMTX

MediaMTX relays USB and video-file sources to the dashboard. RTSP cameras are read directly and work without it.

5.1Download and unpack PC

BASH
mkdir -p ~/mtx && cd ~/mtx
curl -fSL https://github.com/bluenviron/mediamtx/releases/download/v1.21.1/mediamtx_v1.21.1_linux_arm64.tar.gz -o mediamtx.tar.gz
file mediamtx.tar.gz
tar -xzf mediamtx.tar.gz
ls
mediamtx.tar.gz: gzip compressed data
LICENSE  mediamtx  mediamtx.tar.gz  mediamtx.yml
  • mkdir -p ~/mtx && cd ~/mtx makes a work folder and enters it
  • curl -fSL adds -f, so a wrong URL fails instead of saving an error page
  • file reports the real file type, and it must say gzip
  • tar -xzf extracts (x) a gzip (z) archive from a file (f)
  • ls lists the result: the mediamtx program and its mediamtx.yml config
Pick the right file: use linux_arm64, not armv6, armv7 or amd64. "Not in gzip format" means you saved an error page.

5.2Check the config PC

BASH
grep -n -A2 "^paths:" mediamtx.yml

Why: grep searches text. -n shows line numbers, -A2 shows 2 lines after, and "^paths:" matches that word at line start. You should see all_others: below it, the setting that made streaming work here.

5.3Send to the board PC

BASH
adb shell mkdir -p /home/root/mediamtx
adb push mediamtx /home/root/mediamtx/mediamtx
adb push mediamtx.yml /home/root/mediamtx/mediamtx.yml

Why: adb shell mkdir creates a folder on the board. adb push source destination copies a file from the PC to the board over USB.

5.4Check on the board Board host

BASH
chmod +x ~/mediamtx/mediamtx
file ~/mediamtx/mediamtx
~/mediamtx/mediamtx --version
/root/mediamtx/mediamtx: ELF 64-bit LSB executable, ARM aarch64 ...
v1.21.1

Why: The copied file loses its executable flag, so chmod +x restores it. file must say ARM aarch64, and --version proves it runs. "Exec format error" means the wrong architecture.

§ 06Starter Kit Board host

6.1Download the kit

BASH
cd ~
curl -fsSL https://github.com/WG-Tech-Solutions/Starter-Kit-Advanced/archive/refs/heads/main.tar.gz -o kit.tar.gz
tar -xzf kit.tar.gz
cd ~/Starter-Kit-Advanced-main
chmod +x *.sh
ls
  • cd ~ goes to your home folder
  • curl -fsSL is a quiet download (-s) that still shows errors and follows redirects
  • tar -xzf unpacks it into Starter-Kit-Advanced-main
  • chmod +x *.sh makes every script (*.sh) executable

6.2Point MediaMTX at your config

BASH
sed -i "s#/etc/mediamtx.yml#$HOME/mediamtx/mediamtx.yml#" start_voyager.sh
grep -n "nohup mediamtx" start_voyager.sh
nohup mediamtx /root/mediamtx/mediamtx.yml > /tmp/mediamtx.log 2>&1 &

Why: The script looks for its config in /etc, which is read-only on this board. sed edits text: -i changes the file in place and s#old#new# replaces the old path with your home copy. The grep confirms the change.

6.3Make sure the container is running

BASH
docker start Voyager-SDK
docker ps | grep -i voyager
docker exec Voyager-SDK bash -lc 'ls -d /home/ubuntu/voyager-sdk'
/home/ubuntu/voyager-sdk
  • docker start starts the stopped container. The kit cannot use a stopped one
  • docker ps | grep -i voyager shows only running containers, filtered (| pipes output to grep, -i ignores case)
  • docker exec runs one command inside the container, here checking the SDK folder exists

6.4Launch, in one terminal window

BASH
cd ~/Starter-Kit-Advanced-main
export PATH=$HOME/mediamtx:$PATH
export CONTAINER=Voyager-SDK
export VOYAGER_SDK_VERSION=1.6.0
command -v mediamtx
./start.sh
Setup complete
  Voyager container : Voyager-SDK
  SDK path          : /home/ubuntu/voyager-sdk
  Metis driver      : 1.4.16
  AIPU cores        : 4
  • export PATH=... lets the shell find mediamtx by name
  • export CONTAINER=Voyager-SDK is essential. The script defaults to lowercase voyager-sdk and Docker names are case-sensitive, so without it a second container is created
  • export VOYAGER_SDK_VERSION tells the kit which SDK version to use
  • command -v mediamtx prints where the shell found it, proving the PATH works
  • ./start.sh runs five steps: environment setup, image download, MediaMTX and inference server, dashboard, health check
Do not press Ctrl+C during the image download. The exports last only in this terminal window, so use the same one. If step 3 says "mediamtx not found on PATH", re-run the PATH export and ./start.sh, which is safe to repeat.

6.5Verify

BASH
docker ps -a
tail -f /tmp/mediamtx.log
docker exec Voyager-SDK tail -f /tmp/ai_server.log

Why: docker ps -a should still show one Voyager container (Compose adds its own dashboard containers, which is normal). tail -f follows a log file live, and Ctrl+C stops it. MediaMTX serves RTSP on port 8554 and HLS on 8888. Then open the dashboard and use Add Model for your camera.

§ 07Troubleshooting

Symptom Cause and fix
docker: command not found Wrong shell (PC, bare sh-5.1# or inside the container). Use the board host as root.
Container "is not running" Run docker start Voyager-SDK.
axdevice: command not found Not in the container or venv. Run source venv/bin/activate in ~/voyager-sdk.
Failed to open device metis Driver and SDK versions differ. Compare /sys/class/metis/version with the SDK.
not in gzip format The download was an error page. Use curl -fSL and check with file.
Exec format error Wrong architecture. Use arm64 builds only.
Second Voyager container CONTAINER was not set. Set it, remove the extra container and rerun.
adb devices -l empty Use a data cable, replug, then restart the adb server.

More help: community.axelera.ai and docs.axelera.ai.

§ 08Power off and power on Board host

After a reboot the container is stopped and your export settings are gone, so the kit needs restarting the same way each time.

8.1Shut down safely

BASH
exit                      # only if you are inside the container
docker stop Voyager-SDK
poweroff
  • exit leaves the container and returns you to the board host (prompt root@antelao-3588)
  • docker stop Voyager-SDK stops the container cleanly so nothing is cut off mid-write
  • poweroff shuts the board down. If it is not available, use shutdown -h now

Wait until the board is fully off before unplugging the power cable.

8.2Power on and open a shell

Connect the DC power cable. The board boots by itself. Wait a minute or two, then on the PC:

BASH
adb devices -l
adb -s usb:2-5 shell

The first command checks the PC sees the board again. The second opens a shell on it. Use your own usb:X-Y value, or ssh antelao@<board-ip> instead. The prompt must read root@antelao-3588.

8.3Start the container

BASH
docker start Voyager-SDK
docker ps | grep -i voyager
417fdc522ae6   axelera-sdk-ubuntu-2204-arm64:1.6.0   ...   Up 5 seconds   Voyager-SDK

docker start brings the stopped container back. The second command shows only running containers, so seeing Voyager-SDK with Up means it works.

8.4Set the variables and launch the kit

BASH
cd ~/Starter-Kit-Advanced-main
export PATH=$HOME/mediamtx:$PATH
export CONTAINER=Voyager-SDK
export VOYAGER_SDK_VERSION=1.6.0
command -v mediamtx
./start.sh
/root/mediamtx/mediamtx

These export lines only last in the current terminal window, so a reboot erases them. Without CONTAINER the kit looks for a lowercase voyager-sdk, and without VOYAGER_SDK_VERSION it stops with an error. command -v mediamtx proves the shell can find MediaMTX before you launch.

After any reboot, the whole restart is then just:

BASH
docker start Voyager-SDK
source ~/kit-env.sh
cd ~/Starter-Kit-Advanced-main && ./start.sh

source loads the saved lines into your current terminal. && runs the kit only if cd succeeded.

Tip: Afterwards docker ps -a should still show one Voyager container. If you see voyager-sdk in lowercase, the variables were not set. Set them, remove the extra container and rerun.

§ 09Quick Reference

9.1Every boot

BASH
modprobe metis
cd ~/Starter-Kit-Advanced-main
./start.sh
  • modprobe metis loads the Metis driver into the system. It makes sure the AIPU is available after a boot
  • cd ~/Starter-Kit-Advanced-main goes into the kit folder
  • ./start.sh starts everything (MediaMTX, inference server, dashboard)
Tip: After a full power-off, start the container and set the variables first, as shown in section 8.

9.2Useful commands

BASH
# dashboard logs
docker compose logs -f backend

# inference logs
docker exec Voyager-SDK tail -f /tmp/ai_server.log

# what is running on the AIPU
docker exec Voyager-SDK curl -s http://localhost:8001/inference/status

# is the backend alive
curl -s http://localhost/api/health

# restart everything
./stop.sh && ./start.sh
  • docker compose logs -f backend shows the dashboard backend's log live (-f keeps following). Run it inside the kit folder
  • docker exec Voyager-SDK tail -f /tmp/ai_server.log follows the inference server's log inside the container
  • curl -s http://localhost:8001/inference/status asks the inference server (port 8001) what it is running. -s keeps curl quiet. It runs through docker exec so localhost means the container
  • curl -s http://localhost/api/health checks that the dashboard backend answers
  • ./stop.sh && ./start.sh stops everything, then starts it again only if the stop worked

Press Ctrl+C to leave a live log.

9.3Golden diagnostic

This exercises the board with none of the kit's code in the way:

BASH
docker exec Voyager-SDK bash -lc \
  'cd /home/ubuntu/voyager-sdk && source venv/bin/activate && \
   ./inference.py yolov8n-coco "<rtsp-url>" --no-display --show-stats --frames 50'
  • docker exec Voyager-SDK bash -lc '...' runs the quoted commands inside the container in a login shell. The \ at a line end just continues the command on the next line
  • cd ... && source venv/bin/activate enters the SDK folder and turns on its Python environment
  • ./inference.py yolov8n-coco "<rtsp-url>" runs the yolov8n-coco model on your camera stream. Replace <rtsp-url> with your camera's address
  • --no-display opens no window, --show-stats prints speed numbers and --frames 50 stops after 50 frames
If that tool works but the dashboard does not, the problem is in the kit, so collect logs. If it fails too, the problem is below the kit, so recheck sections 3 to 5.

§ 10FAQ & Troubleshooting

networkThe dashboard will not load at http://localhost. Check the containers: docker compose ps. If the backend is restarting, view docker compose logs backend --tail=30. A common cause is a mapped USB camera that is not plugged in. Re-run ./setup.sh, which handles it.

networkStreams fail with "MediaMTX HLS not ready". The Docker bridge gateway moved after a reboot. Run docker compose down && docker compose up -d. The kit pins the subnet so this self-corrects.

inferenceStreams run but there are no boxes. Almost always the model's label filter is set to a class that is not in your scene, so every detection is discarded silently. Class 0 is person. Make sure the filter includes what you actually want to detect.

inferenceThe AIPU seems slow (~17 fps). The model is using one of the four AIPU cores. The dashboard forces all four. If you are testing with inference.py directly, add --aipu-cores 4.

hardwareaxdevice finds no device. The driver is not loaded, or a stale handle is held. Run modprobe metis, check lsmod | grep metis, and if needed power-cycle the board (not just reboot).

networkA camera will not connect. Test it with ffprobe first. The usual causes: the camera is on a different subnet, credentials are missing from the URL, or the stream path is wrong. A camera that is unreachable is isolated; the other cameras keep running.

setupThe video timestamp is hours off from the real time. The board runs UTC by default; cameras usually burn in local time. Set TZ in the kit's .env if you want them to agree. This is cosmetic, not a fault.

docker"sudo: command not found", or Docker permission errors. This board logs in as root and has no sudo, which is expected. Run every command without sudo (drop the word). Do not try to install sudo via apt; the stock image has no package repositories. As root, Docker already works with no group setup.

inferenceLatency grows the longer a session runs. Usually stacked sessions competing for the AIPU. ./stop.sh && ./start.sh clears it. A steady one-to-two-second delay, on the other hand, is normal.
