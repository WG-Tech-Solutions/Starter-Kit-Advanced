Compute Board Setup Guide

WGtech AI Starter Kit
Metis Compute Board

End-to-end setup for the Axelera Metis Compute Board — an RK3588 single-board computer with an integrated 4-core Metis AIPU. This guide takes you from a blank board to running multi-camera Vision AI inference in a browser. Follow each section in order; the steps depend on one another.

⏱️
Estimated Time:
  • Active setup time: ~30–60 minutes
  • Total time (including downloads & the first model compile): 2–4+ hours
Product
AI Starter Kit
Platform
Metis Compute Board (RK3588)
Accelerator
Integrated Metis AIPU · 4 cores
🧭
Different board? This guide is for the Metis Compute Board, where the AIPU is built into the SBC. If you have the Raspberry Pi 5 + Metis M.2 unit, use the Pi Starter Kit instead — its PCIe steps do not apply here.
§ 01

Hardware Requirements

The Metis Compute Board is a complete unit — the AIPU is on the board, so there is no card to seat and no PCIe HAT to stack. You will need the following around it:

ComponentNotes
Metis Compute BoardRK3588 SBC with integrated Metis AIPU — supplied as one unit
Power supplyUse the PSU specified by Axelera for your board revision. An underpowered supply causes random crashes and AIPU instability
StorageSD card or eMMC/NVMe as specified for your board. Class 10 / A2 or faster shortens boot and install times
HDMI display + cableCheck the board's connector type before buying a cable
USB keyboard + mouseFor initial setup
Ethernet (preferred) or Wi-FiEthernet is strongly preferred for reliability during large downloads
One or more RTSP IP camerasOn the same subnet as the board. H.264 or H.265, both supported. A USB webcam works too
✅
Integrated AIPU Unlike the Pi kit, the Metis Compute Board has the AIPU built in. There is no physical accelerator installation — no card, no M.2 slot, no PCIe HAT to worry about.
§ 02

Flash the Operating System

Flash the board's OS image following Axelera's official documentation for your board revision. Axelera's guide is authoritative — image, tool, and procedure vary by board, so follow theirs rather than a generic one.

📖
Start at docs.axelera.ai and the Voyager SDK repository. Use the image and flashing tool they specify for the Compute Board.

Once flashed, boot the board and confirm you are on the right platform:

bash
uname -m
cat /proc/device-tree/model
Expected output
aarch64
...RK3588...
⚠️
If uname -m does not report aarch64, or the model does not mention RK3588, stop and recheck the image. The rest of this guide assumes a correctly flashed Compute Board.
§ 03

First Boot & Opening the Terminal

Complete the on-screen first-boot setup (locale, user, network). Then open a terminal — every command in this guide runs there.

1Connect to the network

Ethernet is plug-and-go. For Wi-Fi, use the desktop network menu or your board's setup tool. Confirm you are online and note the board's IP — you will use it to reach the dashboard from your laptop later:

bash
ping -c 3 8.8.8.8
hostname -I
💡
Write down the IP from hostname -I (the first address). You will open http://<that-ip> from another machine on the same network once the dashboard is running.
§ 04

System Update

Bring the system up to date before installing anything else:

bash
sudo apt update && sudo apt upgrade -y
⏳
This can take a while on first run depending on how old the image is. Use Ethernet if you can.

Install a few basics used later:

bash
sudo apt install -y curl git ffmpeg
§ 05

Install Docker

The dashboard runs in containers. Install Docker Engine and the Compose plugin:

bash
curl -fsSL https://get.docker.com | sudo sh
1Run Docker without sudo

Add your user to the docker group so the kit's scripts can talk to Docker directly:

bash
sudo usermod -aG docker $USER
🔁
Log out and back in (or reboot) for the group change to take effect. Skipping this is the most common early mistake — the scripts assume Docker works without sudo.
2Verify
bash
docker run hello-world
docker compose version
Expected output
Hello from Docker!
...
Docker Compose version v2.x.x
🚫
If docker run hello-world only works with sudo, the group change has not applied yet. Log out and back in, then retry — do not work around it with sudo, or the kit's scripts will hit permission errors later.
§ 06

Metis Driver & Runtime

The AIPU is driven by the metis kernel module. Install it using Axelera's instructions for your BSP, then confirm it is loaded:

bash
lsmod | grep metis
cat /sys/module/metis/version
Expected output
metis                 131072  0
1.4.16

If the module is not loaded:

bash
sudo modprobe metis
1Load automatically at boot

So you do not have to modprobe after every reboot:

bash
echo metis | sudo tee /etc/modules-load.d/metis.conf
🔢
The driver version (here 1.4.16) and the Voyager SDK are versioned together. Keep them matched — installing a mismatched pair is a common source of AIPU errors later.
🔧 Debug: module will not load

Check kernel messages for the reason:

bash
sudo modprobe metis
dmesg | grep -i metis | tail -n 20

A full power cycle — not a reboot — clears a surprising number of AIPU issues. Disconnect power, wait a few seconds, and boot again.

§ 07

Voyager SDK Container

Install the Axelera Voyager SDK using their setup script for your version. It creates a Docker container that holds the SDK and its dependencies — this is where inference actually runs.

📦
Follow Axelera's SDK installation for the Compute Board. When it finishes, a container named Voyager-SDK (or voyager-sdk) will exist.
1Confirm the container exists
bash
docker ps -a | grep -i voyager
Expected output
...   Voyager-SDK
🔠
Note the exact name and capitalisation. Axelera's tooling has shipped this as both Voyager-SDK and voyager-sdk. The Starter Kit detects it automatically, but it helps to know which you have.
2Find the SDK path inside it
bash
docker exec Voyager-SDK ls /home/ubuntu/voyager-sdk
§ 08

Verify Inference — the step that matters

This is the checkpoint. If inference runs here, the hardware is ready and the Starter Kit will work. If it does not, no amount of dashboard configuration will help — so do not move on until this passes.

1The AIPU is visible
bash
docker exec Voyager-SDK bash -lc \
  'cd /home/ubuntu/voyager-sdk && source venv/bin/activate && axdevice'

The Metis device should be listed. If not, the driver is not loaded or the container cannot reach it — return to §06.

2Inference runs
bash
docker exec Voyager-SDK bash -lc \
  'cd /home/ubuntu/voyager-sdk && source venv/bin/activate && \
   ./inference.py yolov8n-coco media/traffic1_1080p.mp4 \
   --no-display --show-stats --frames 50'
Expected output
========================================================
Element                          Time(us)   Effective FPS
========================================================
...
inference-task0:inference          15,401            64.9
========================================================
End-to-end : 64.9fps
🎯
If you see a frames-per-second figure, the hardware is ready. Around 65 fps on this board means all four AIPU cores are working. Continue to the next section and install the Starter Kit.
🛑
No FPS figure? Stop here. Everything downstream depends on this. Re-check §06 (driver) and §07 (SDK), power-cycle the board, and retry. This tool exercises the board, driver, SDK, and AIPU with none of the dashboard's code in the way — if it fails, the problem is below the Starter Kit.
🔧 Debug: about AIPU cores & performance

The Metis AIPU on this board has four cores. Model configurations frequently default to aipu_cores: 1, which caps throughput at roughly a quarter (~17 fps instead of ~65). The Starter Kit forces all four cores at runtime, so you get the full figure once the dashboard is running.

You can compare for yourself:

bash
# one core
./inference.py yolov8n-coco media/traffic1_1080p.mp4 --no-display --show-stats --aipu-cores 1 --frames 100
# four cores
./inference.py yolov8n-coco media/traffic1_1080p.mp4 --no-display --show-stats --aipu-cores 4 --frames 100
§ 09

Cameras & Network

The dashboard's main input is RTSP IP cameras. Get them working before the dashboard, where errors are clearer.

🌐
The single most common camera problem: the camera must be on the same subnet as the board, or reachable by a route from it. A camera at 192.168.0.50 is not reachable from a board at 192.168.1.10 without routing between those networks.
1Reach the camera
bash
ping -c 2 192.168.1.69
2Test the RTSP URL
bash
ffprobe -rtsp_transport udp \
  "rtsp://user:pass@192.168.1.69:554/ch0_0.264"

You should see a stream description — codec, resolution, framerate. If ffprobe cannot open it, the dashboard will not either.

Camera vendorTypical RTSP path
Hikvision/Streaming/Channels/101
Dahua/cam/realmonitor?channel=1&subtype=0
Generic/ch0_0.264, /stream1, /live
🎥
Credentials go in the URL: rtsp://user:password@ip:554/path. H.264 (.264) and H.265 (.265) both work and can be mixed in one session.
🔧 Debug: camera drops after ~2 seconds

Some cameras reset an RTSP-over-TCP session after a couple of seconds. The Starter Kit defaults to UDP for exactly this reason. If yours specifically needs TCP, set RTSP_TRANSPORT=tcp in the kit's .env after install.

§ 10

Run the Dashboard

With inference verified (§08) and a camera reachable (§09), install and start the Starter Kit.

1Clone the kit
bash
git clone https://github.com/WG-Tech-Solutions/Starter-Kit-Advanced.git
cd Starter-Kit-Advanced
chmod +x *.sh
2Log in to the image registry (if required)

The dashboard ships as pre-built container images. If they are private, log in once:

bash
docker login
3Start everything
bash
./start.sh

That one command detects your board's configuration, pulls the images, starts the inference stack, and brings up the dashboard:

Expected output
=====================================================
  WGtech AI Dashboard is running
=====================================================
  Dashboard:    http://localhost
  From another machine on the LAN:
                http://192.168.1.102
=====================================================
🚀
Open http://localhost on the board, or http://<board-ip> from your laptop on the same network. Then read USER_GUIDE.md to add cameras, deploy a model, and record.
4Stopping
bash
./stop.sh
🔁
After a reboot: run sudo modprobe metis (unless you enabled auto-load in §06), then ./start.sh. Running ./start.sh again is always safe and is the first thing to try if anything looks wrong.

Quick Reference

Every boot:

bash
sudo modprobe metis
cd ~/Starter-Kit-Advanced
./start.sh

Useful commands:

bash
# dashboard logs
docker compose logs -f backend

# inference logs
docker exec Voyager-SDK tail -f /tmp/ai_server.log

# what is running on the AIPU
docker exec Voyager-SDK curl -s http://localhost:8001/inference/status

# is the backend alive
curl -s http://localhost/api/health

# restart everything
./stop.sh && ./start.sh

Golden diagnostic — exercises the board with none of the kit's code in the way:

bash
docker exec Voyager-SDK bash -lc \
  'cd /home/ubuntu/voyager-sdk && source venv/bin/activate && \
   ./inference.py yolov8n-coco "<rtsp-url>" --no-display --show-stats --frames 50'
🧭
If that tool works but the dashboard does not, the problem is in the kit — collect logs. If it fails too, the problem is below the kit — recheck §06–§08.

FAQ & Troubleshooting

network The dashboard will not load at http://localhost. Check the containers: docker compose ps. If the backend is restarting, view docker compose logs backend --tail=30. A common cause is a mapped USB camera that is not plugged in — re-run ./setup.sh, which handles it.
network Streams fail with "MediaMTX HLS not ready". The Docker bridge gateway moved after a reboot. Run docker compose down && docker compose up -d — the kit pins the subnet so this self-corrects.
inference Streams run but there are no boxes. Almost always the model's label filter is set to a class that is not in your scene, so every detection is discarded silently. Class 0 is person — make sure the filter includes what you actually want to detect.
inference The AIPU seems slow (~17 fps). The model is using one of the four AIPU cores. The dashboard forces all four; if you are testing with inference.py directly, add --aipu-cores 4.
hardware axdevice finds no device. The driver is not loaded, or a stale handle is held. sudo modprobe metis, check lsmod | grep metis, and if needed power-cycle the board (not just reboot).
network A camera will not connect. Test it with ffprobe first. The usual causes: the camera is on a different subnet, credentials are missing from the URL, or the stream path is wrong. A camera that is unreachable is isolated — the other cameras keep running.
setup The video timestamp is hours off from the real time. The board runs UTC by default; cameras usually burn in local time. Set TZ in the kit's .env if you want them to agree. This is cosmetic, not a fault.
docker docker only works with sudo. The group change from §05 has not applied. Log out and back in (or reboot). Do not work around it with sudo — the kit's scripts expect Docker to work as your user.
inference Latency grows the longer a session runs. Usually stacked sessions competing for the AIPU. ./stop.sh && ./start.sh clears it. A steady one-to-two-second delay, on the other hand, is normal.
